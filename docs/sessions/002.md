## Decisions

### Camera placement: src/camera.zig vs src/renderer/camera.zig
- The renderer directory (`src/renderer/`) contains OpenGL-abstraction modules
  (shader, mesh) that import C types via `@cImport`.
- The camera module needed to import `math.zig`, which lives in `src/`. If
  camera.zig stays in `src/renderer/`, it would use `@import("../math.zig")` —
  a cross-directory import that fails for standalone test modules in Zig 0.16
  ("import of file outside module path").
- Solution: place camera.zig in `src/` alongside math.zig. This keeps
  co-located imports working and allows standalone testing.

### No shared c.zig module
- Attempted creating `src/c.zig` as a shared C import module so all files
  would use the same `GLFWwindow` type.
- This failed because test modules in `src/renderer/` couldn't import `../c.zig`
  (same "outside module path" error).
- Reverted to each file having its own `@cImport` block.
- To avoid the `GLFWwindow` type mismatch between modules, key polling is done
  in main.zig (which owns the window handle) and only `c_int` values (primitive,
  universally compatible) are passed to `Camera.processKey()`.

### Key polling vs processInput
- First attempt: `Camera.processInput(window: *c.GLFWwindow, dt: f32)` — this
  type is module-specific (each `@cImport` creates distinct opaque structs).
- Final approach: poll keys in main.zig, call `Camera.processKey(key, action, dt)`
  with `c_int` values (primitive `i32`, same type across all modules).

## Key Learnings
- **Zig 0.16 addTest does not collect tests from imported modules** when using
  `b.addTest(.{ .root_module = exe_mod })` with a module that has `.link_libc = true`.
  Standalone test modules (created via `b.createModule` with `root_source_file`)
  DO collect imported module tests.
- **Cross-directory @import fails for standalone Zig test modules.** A file at
  `src/renderer/foo.zig` cannot `@import("../bar.zig")` when compiled as a
  standalone test target.
- **c_int is universally compatible across @cImport blocks** in Zig — only
  opaque struct types (like `GLFWwindow`) are module-specific.
- **Each @cImport creates its own namespace** for types. Two files with separate
  `@cImport` blocks get distinct `GLFWwindow` types even from the same header.
